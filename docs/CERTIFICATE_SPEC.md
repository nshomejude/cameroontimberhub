## Part B — 16-Layer Certificate Security Architecture

> The security-engineering companion to Part A: each of the 16 layers gets a defined threat model, mechanism, implementation approach, validation method, and failure behavior — not just a visual description.

**Ring 1 — Digital Identity & Cryptographic Security (Layers 1–7):** unique certificate identity (public ID, never the DB primary key) · cryptographically random verification token (separate from the certificate ID, high entropy, never `md5`/`sha1` of the ID) · canonical certificate record (one deterministic machine-readable JSON representation — the actual source of truth, not the PDF) · SHA-256 hash of the canonical record · digital signature/electronic seal over the hash (issuer authenticity — a hash alone only proves integrity, not who issued it) · protected signing-key infrastructure (KMS/HSM-style separation — the application asks a signing service to sign, it never holds the private key directly; key lifecycle: create/activate/rotate/retire/compromise/replace) · trusted timestamp on creation/approval/signing/issuance events.

**Ring 2 — Verification & Provenance Security (Layers 8–14):** dynamic QR pointing at a live verification URL (never embeds the full certificate) · live status & revocation registry (DRAFT/SUBMITTED/UNDER_REVIEW/VERIFIED/ISSUED/ACTIVE/SUSPENDED/REVOKED/SUPERSEDED/REPLACED/WITHDRAWN — revoked certificates are never deleted) · certificate version control (material changes create a new version with its own snapshot/hash/signature/timestamp/reason/actor, never edit-in-place) · evidence manifest integrity (every evidence file individually SHA-256 hashed, aggregated into a manifest hash bound to the certificate) · geospatial integrity (canonical GeoJSON → hash → certificate binding; point coordinates to ≥6 decimal digits per EUDR, polygons for plots >4ha) · chain-of-custody & quantity binding (an allocation ledger against the certified quantity — prevents the same certificate being over-claimed across multiple shipments) · immutable audit trail (every lifecycle event: actor, action, entity, timestamp, before/after — administrators cannot silently erase it).

**Ring 3 — Physical Anti-Counterfeiting (Layers 15–16):** visual security (microtext, guilloche pattern, variable security background derived from the certificate's own fingerprint, variable watermark, fine-line security frame) · serialized physical authentication (serialized security seal, holographic element, UV feature, tamper-evident seal, security paper — all requiring a real, controlled physical supplier relationship TimberHub does not yet have).

**Core principle stated by the spec:** cryptography is stronger than appearance; live verification is stronger than the printed certificate; the evidence ledger is stronger than the certificate PDF. The certificate is a signed snapshot of the underlying evidence state, not the evidence itself. A counterfeiter must defeat all 16 layers — defeating one (e.g., copying a genuine QR onto a fake PDF) exposes the fraud via the others (the QR still resolves to the *genuine* data, which won't match the fake document).

## Scope decision (read before building)

**What exists today:** nothing. `grep -rl certificate app/Models app/Services database/migrations` finds zero certificate-related models, services, or tables — this is a greenfield subsystem, not a migration of an existing one.

**Why this isn't being built as one 16-layer pass:** Rings 1 and 2 (Layers 1–14) are pure software — a data model, a signing service, a QR/verification endpoint, an audit trail, a quantity ledger. They can be built correctly and tested today. Ring 3 (Layers 15–16) requires things this plan cannot responsibly assume into existence: a real print supplier relationship, a hologram/UV-label vendor with serial-range control, a physical inventory/reprint-tracking process run by real staff, and print-hardware testing (microtext legibility, QR scan reliability after printing) that only makes sense once physical certificates are actually being issued. Building Ring 3's code against imagined supplier APIs and imagined print-test results would be exactly the kind of fabricated-infrastructure mistake this project's rules exist to prevent (see `CTH_Claude_Code_Build_Brief.md` rule 0.3 and the PEFC integration precedent — deferred with an honest reason, not silently skipped or faked).

**What's actually being built first — gap-plan item 0.8 "Certificate — Digital Core":** Rings 1 + 2 in full (Layers 1–14): canonical certificate record + versioning, SHA-256 hashing, an application-level signing service (real asymmetric signing via Laravel's own key-management primitives — not a fabricated HSM integration, but genuinely separated from a broadcastable secret, with an explicit note that a KMS/HSM upgrade is the documented next step, not pretended to already exist), the status/revocation registry, the evidence manifest hash, geospatial GeoJSON hash and validation, a quantity-allocation ledger, the immutable audit trail, the dynamic QR + public verification page, and a certificate PDF that renders everything Ring 1+2 can honestly support (identity, data, QR, fingerprint, authenticity panel, map, evidence panel, issuance block) — using the *existing* house `.article-prose`/hand-styled-Tailwind pattern, no fabricated typography plugin, consistent with how every other document-style page in this codebase is built.

**Explicitly deferred, tracked as item 0.8b "Certificate — Physical Production Layer":** guilloche/microtext/variable-watermark *print-security* generation, the physical certificate serial + copy registry, print-batch tracking, hologram/UV/tamper-seal integration, and the supplier/inventory registries — blocked on a real decision about which physical tier (Standard/Enhanced/High-Assurance) TimberHub actually wants to fund and which print/security-label suppliers it engages, which is a business decision, not an engineering one.

See `docs/GAP_PLAN.md` for the authoritative task breakdown and phase placement of 0.8 and 0.8b.
